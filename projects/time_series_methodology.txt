
# Methodology for Checking Correctness of Students' Work on Big Data Solutions

This methodology outlines the step-by-step process to verify the correctness of a student-deployed big data solution in a Kubernetes cluster. It includes functional, non-functional, and formal capability checks, alongside reserved object names, workload testing, and other critical aspects.

## Prerequisites
To begin the validation process, ensure that the following are available:
- Access to the Kubernetes cluster where the solution is deployed.
- Tools for interacting with SQL/NoSQL databases (e.g., ClickHouse client) and HTTP clients for web requests.
- Data generation and ingestion mechanisms implemented in the project (e.g., Kafka for ingestion).
- A set of predefined testing scripts and metrics gathering tools (e.g., Grafana for monitoring performance metrics).

## Reserved Object Names
| Name                | Object Type     | Description                                          |
|---------------------|-----------------|------------------------------------------------------|
| `sensor_data_raw`    | ClickHouse Table| Stores raw sensor data as generated by the sensors.   |
| `sensor_lens`        | ClickHouse Table| Stores aggregated sensor data for the user interface. |
| `data_ingestor`      | Kubernetes Job  | Handles data ingestion into ClickHouse.               |
| `workload_generator` | Kubernetes Job  | Generates simulated workloads for testing purposes.   |
| `request_handler`    | Kubernetes Pod  | Receives and processes user requests for data.        |
| `kafka_topic_sensors`| Kafka Topic     | Intermediate storage for sensor data before ingestion.|

## Step-by-Step Checks

### 1. Checking for the Presence of Required Objects
Ensure that the required objects are deployed and properly configured.

#### Kubernetes Cluster
- Run `kubectl get pods,services,jobs` to verify the presence of `data_ingestor`, `workload_generator`, and `request_handler`.
  
#### ClickHouse Tables
- Query the ClickHouse tables to ensure they exist:
  ```sql
  SHOW TABLES FROM default;
  ```

Expected output should include:
- `sensor_data_raw`
- `sensor_lens`

### 2. Checking Functional Capabilities
Validate the functional capabilities of the deployed solution.

#### Data Ingestion Validation
Ensure that data ingestion from Kafka to ClickHouse is working correctly:
- Check for incoming data in the raw data table:
  ```sql
  SELECT COUNT(*) FROM sensor_data_raw;
  ```

- Ensure data aggregation into the lens table:
  ```sql
  SELECT COUNT(*) FROM sensor_lens;
  ```

#### Query Validation
Ensure that queries to the `sensor_lens` table return correct aggregated results:
- Example: Retrieve lens data for a specific sensor over a given time range.
  ```sql
  SELECT * FROM sensor_lens WHERE sensor_id = 1 AND timestamp BETWEEN '2024-09-01' AND '2024-09-10';
  ```

### 3. Checking Formal Restrictions
Validate that the solution adheres to formal restrictions provided in the project description.

#### Data Retention
Ensure that data from sensors is retained for at least one month:
- Query ClickHouse to check for data older than one month:
  ```sql
  SELECT MIN(timestamp) FROM sensor_data_raw;
  ```

#### Replication and Sharding
Ensure replication and sharding are correctly implemented:
- Check replication status:
  ```sql
  SELECT * FROM system.replicas WHERE table = 'sensor_data_raw';
  ```

### 4. Checking Fault-Tolerance (if applicable)
If the solution describes fault-tolerant capabilities, validate the following:

#### Node Failure Simulation
Simulate a node failure in Kubernetes to test fault tolerance:
- Run `kubectl drain <node_name>` and check if the solution continues working without data loss.

#### Data Recovery Validation
After node failure, ensure that data is correctly recovered by running:
  ```sql
  SELECT COUNT(*) FROM sensor_data_raw;
  ```

Compare results before and after the failure.

### 5. Workload Testing

#### Test Description
Workload tests ensure that the solution can handle concurrent requests, data ingestion, and query loads under various scenarios.

##### Data Generation and Ingestion
- Simulate 1000 sensors generating data at 1kHz frequency, batch sent every 3-4 seconds:
  - Each batch contains 3,000 to 4,000 data points.
  - Data should be ingested using Kafka.

##### Request Workload
- Simulate 100 users querying data from the `sensor_lens` table, each requesting 1-10 sensors over a specific time range.
- Example query for workload testing:
  ```sql
  SELECT * FROM sensor_lens WHERE timestamp BETWEEN '2024-09-01' AND '2024-09-02';
  ```

##### Frequency and Volume
- Generate requests at the rate of 10 requests/second, sustained for 5 minutes.
- Measure the response time and query completion rates.

##### Metrics to Measure
- Average and peak latency (measured in milliseconds).
- Query success rate (% of successful queries).
- Data ingestion throughput (measured in rows/second).

#### Tools for Monitoring
- Use Prometheus and Grafana for real-time monitoring of the system's performance.
  - Monitor CPU, memory, and disk usage on the Kubernetes cluster.
  - Track Kafka throughput and ClickHouse query performance.

---

By following this methodology, students' work can be comprehensively validated to ensure correctness, performance, and adherence to formal restrictions and functional requirements.
